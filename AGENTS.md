# Development guidance

1. Start with the linked GitHub Issue. Include acceptance criteria and use one PR per coherent change.
2. Use OpenSpec's spec-driven flow in `openspec/changes/<slug>`: proposal, spec deltas, design, tasks. Update tasks to reflect tested work, not intentions.
3. Capture architectural trade-offs as numbered ADRs, status proposed/accepted/superseded.
4. Reuse `@tazumo/core` for domain logic and `@tazumo/brand` for independently changeable brand tokens. Do not couple user identity, currency or region to the brand name.
5. Do not ship mock courier positions, payments, fees or ETAs as real. The MVP is demonstrative.
6. Never commit secrets, customer data, .env files, EAS credentials or private repository tokens.
7. Require accessibility and language checks before marking customer-facing features complete. Prefer functional usability over mascot decoration.
8. Link pull requests and commits to relevant issues. Prefer draft PRs until CI and native builds have evidence.

## Mandatory Issue → OpenSpec → PR → evidence workflow

**All repository changes must be delivered through pull requests. Never commit directly to `main`**, including documentation, workflows, dependencies, fixtures, tests and agent instructions. Branch from current `main` and keep PRs small enough to review. Do not merge an unrelated change just because a PR is already open.

1. **Issue first.** Before coding, identify an existing GitHub Issue or create a new one. Record the problem and context, desired user/demo behavior, scope and out-of-scope, affected platforms/repositories, explicit acceptance criteria, risks/dependencies and verification plan. For defects capture expected vs actual behavior and reproduction. Link related or blocking issues. Avoid duplicate tracking issues.
2. **Specify before implementing.** For functional/behavior changes create or update an OpenSpec change in `openspec/changes/<slug>/` with proposal, requirements/scenarios, design when helpful, and executable tasks. Link the Issue number in the proposal. Use ADRs for durable architectural trade-offs, with alternatives, consequences, date and status. Minor editorial fixes may reference the Issue without a new ADR or OpenSpec change, but still require a PR.
3. **Implement on a branch, submit a PR.** Use `feat/<issue>-<short-description>` or `fix/<issue>-<short-description>`; opening a draft PR early is encouraged. The PR description must contain `Refs #<issue>` or `Closes #<issue>` as appropriate, summary, changed behavior, OpenSpec/ADR links, test commands and *observed* results, screenshots/artifacts for UI/native changes, migration/rollback notes where relevant, and known limitations. Cross-repository changes must link the paired PRs/issues and the exact Tazumo SUT contract version.
4. **Verify before merge.** Run and report relevant unit, contract, quality, E2E, device, accessibility and security checks. Distinguish mocked/offline tests, browser execution, Appium device runs and live Wopee runs. Never mark a task verified based solely on code written, a queued CI job, or an inferred result. A failed/blocked check stays visible in the PR and Issue; do not silently bypass it.
5. **Review and merge.** Resolve review feedback, confirm required CI checks and approvals, merge via PR only, and delete the merged feature branch. Don't close an Issue until acceptance criteria are verified and linked evidence is recorded. If more work remains, keep it open and document what is pending, or split out a follow-up issue before closure. Update OpenSpec task checkboxes and ADR status as changes land.
6. **Maintain traceability.** PR title/body, commit history, Issues, OpenSpec, ADRs and test artifacts must make it possible to answer: *why did this change happen, what was changed, how was it tested, what is still incomplete, and which SUT version was used?* Record durable links and exact SHA/build or test-run IDs. Do not paste secrets, personal data or sensitive logs into Issues/PRs.

For demo-specific changes, the four required acceptance dimensions are **Setup, Test Authoring, Test Maintenance and Test Execution**. Use `wopee-io-demos/tazumo` as the canonical SUT and keep `contracts/sut.json` version/locators consistent across the five repositories. Any `sut-*` rename requires downstream migration PRs and negative/positive maintenance evidence.

## Issue-first and pull-request-only delivery policy

**All code, configuration, automation, test, documentation and dependency changes MUST ship through a pull request. Do not push directly to `main`, merge without review, or treat an unmerged branch as delivered.** Exceptions are limited to a documented emergency hotfix, which still requires an issue, retrospective PR and validation evidence.

1. **Open or select a GitHub Issue before implementation.** Record the problem/goal, background, reproduction or baseline where relevant, affected platforms/repos, acceptance criteria including positive and negative cases, non-goals, risks/dependencies and blockers. Link upstream/downstream issues for changes spanning repositories. The current SUT integration is tracked in [#32](https://github.com/wopee-io-demos/tazumo/issues/32) in the respective repository.
2. **Describe the intended change in OpenSpec** under `openspec/changes/<slug>/`: proposal referencing the issue, behavior/spec delta, design where needed, task checklist and verification plan. Add or update an ADR when introducing/changing technology, interfaces, release strategy, security boundaries or other durable trade-offs. For documentation-only housekeeping, a concise OpenSpec note can be used when no behavior changes.
3. **Implement on a dedicated branch and open a draft PR early.** Put `Refs #<issue>` in the description; use `Closes #<issue>` only when the PR really satisfies all acceptance criteria. Detail what/why/how, affected apps/repos, scope boundaries, decisions/trade-offs, migration/rollback and how to reproduce tests. Preserve links to originating Issue, OpenSpec and ADR.
4. **Record real evidence.** Include commands, CI run links, screenshots/logs/artifacts where relevant, OS/device versions and results for web/iOS/Android, plus any untested conditions. Differentiate offline simulation, mocked MCP, CI compilation, Appium device test, Wopee-hosted run and production deployment. Never mark a checklist item done based on intent or a pending/failed workflow.
5. **Review and merge only when the applicable gates pass.** Require current-head quality/security checks, reproducible tests, appropriate code review and approval, no unresolved critical findings, and compatibility/contract checks in downstream demo repositories. Merge via GitHub PR; then update the Issue/OpenSpec status with links, verify `main`, and delete the merged feature branch. Keep issues open if device access, hosting, credentials or release validation remain outstanding.
6. **If blocked:** document the precise blocker, how to reproduce it, the owner/unblocking steps, a dependency issue, and what evidence is still missing. Don't weaken assertions, bypass failing checks, disclose secrets or claim an incomplete result succeeded.

### Self-hosted CI runners

The organization may use dedicated Hetzner GitHub Actions runners. Keep workflows on approved runner labels and coordinate runner-label changes through an Issue/PR. Treat untrusted pull-request code as hostile: do not expose package-publication credentials or long-lived secrets to PR jobs, use least-privilege `GITHUB_TOKEN`, isolate ephemeral jobs, and publish only after trusted branch validation. Do not interpret a workflow that failed before runner assignment as a code-test result. Record runner type, environment and artifact provenance in the PR.

## Autonomous review, merge, and cleanup

**Do not stop at opening a PR or wait passively for a person to say "review" or "merge".** The implementation agent owns the complete issue-to-merge lifecycle, including follow-up fixes and issue updates.

1. As soon as the implementation is complete, **spawn independent review subagents when the current execution environment supports them**. Give reviewers separate, focused scopes: (a) correctness and regressions, (b) security/privacy, secrets and dependencies, (c) architecture/OpenSpec/ADR and cross-repo contract compatibility, and (d) test evidence, accessibility and maintainability. The reviewers must inspect the actual diff and acceptance criteria; capture findings and their dispositions in the PR. When independent subagent execution is unavailable, perform the same separate review passes explicitly and label them "self-review", **not** independent human or agent approvals.
2. Fix every blocking finding, run relevant positive/negative tests and request another review pass if changes affect previously reviewed behavior. Record the exact current head SHA, reproducible commands, links to CI runs, and remaining limitations in the issue and PR.
3. **Merge proactively** once GitHub branch protection, actual required approvals, current-head quality/security checks and applicable acceptance criteria are satisfied. Do not request an extra go-ahead solely to merge an already authorized, verified PR. If GitHub requires an independent approval, request it through the supported review mechanism; never fabricate an approval or bypass a required policy.
4. If CI is queued, unavailable, or failed (including runner-unassigned failures), keep the PR open, record a precise blocker issue, and continue other unblocked work. A self-review never replaces a mandatory GitHub approval or a passing required check.
5. After a successful merge, verify the merged SHA and applicable `main` checks, update the originating Issue and OpenSpec with evidence, close only fully accepted work, and **delete the merged feature branch** where the connected tooling/permissions permit. For superseded branches, document the disposition and arrange safe deletion.
6. For coordinated changes across Tazumo and its demo consumers, merge the upstream SUT contract first, verify its exact version, then merge consumer PRs once their compatibility tests pass. Avoid overlapping incompatible contract changes.
7. Never self-approve a PR in GitHub, never disable protection/CI/secret-scanning to make a PR mergeable, and never publish to production or a registry as though test evidence existed when it does not.

This is an **execution policy**, not a promise that any particular session can launch subagents, provision runners, or perform unattended background work. Use actual available automation and record any missing capability as a blocker.

## Autonomous review and merge policy
Do not wait passively for manual review. Request delegated independent review or GitHub Copilot review when available, and self-check code, security, architecture, specs, tests, accessibility and secret exposure. Do not claim subagents were used unless their outputs exist. Fix findings and rerun checks, then merge the PR promptly if required CI is green, acceptance evidence is present and repository protection/approval requirements are satisfied. Self-review cannot replace required independent approval. Never bypass failing checks, CODEOWNERS or a missing runner. Record genuine blockers in linked Issues. Delete merged branches and synchronize OpenSpec tasks.

## Organization Agent Skills standard
Follow https://agentskills.io/specification for reusable agent procedures. Skills are folders containing `SKILL.md` with valid YAML `name` and task-triggering `description`. Use kebab-case names matching the folder, concise progressive-disclosure instructions, and relative `references/`, `scripts/`, `assets/` when useful. Keep `AGENTS.md` for repo-wide policy; do not confuse it with a skill. Validate using `skills-ref validate <skill-folder>` where available, plus meaningful behavior/negative tests. Changes to reusable skills require linked Issues, OpenSpec and PRs; update the upstream `mobile-agent` skills first, then version and synchronize copies to `mobile-demo` with the lockfile. Never claim Wopee MCP or native device validation from mocked results.
